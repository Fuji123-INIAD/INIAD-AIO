# INIAD-AIO v0.3 Course Rule Task Generator Design

作成日: 2026-06-27  
対象: Phase 3-11  
目的: HTML / Slides evidence だけに依存せず、科目ごとの既定ルールから「推定課題」を生成できるようにするための設計メモ。

この文書では方針のみを定義する。v0.3 のこの段階では DB 実装、importer 変更、`backend/main.py` 変更は行わない。

## 1. なぜ course rule が必要か

MOOCs の HTML や Google Slides から課題・提出・期限の evidence を抽出できる場合でも、それだけで課題一覧を安定生成するのは難しい。

理由:

- 科目によって課題の出方が違う。
- 締切が本文に明示されないことがある。
- Slides 内に説明があるが、MOOCs HTML には提出ルールが出ないことがある。
- 課題名が毎週ほぼ同じでも、HTML 上では毎回別表現になることがある。
- SEM101 のように授業運用ルールから「毎回提出がある」と推定できる科目がある。
- COT101 のように、ページ構造から演習・レビュー・小テストを拾えても、締切は授業ルールに従う場合がある。

そのため AIO は、抽出 evidence だけで「確定課題」を作るのではなく、科目ごとの既定ルールから「推定課題」を生成し、HTML / Slides evidence と突き合わせる必要がある。

## 2. deadline_at と estimated_deadline_at

`deadline_at` は、信頼できる明示的な期限として扱う。

例:

- MOOCs HTML に具体的な締切日時がある。
- Slides evidence に具体的な日時があり、抽出精度が十分高い。
- API / 公式データ等から期限が取得できる。

`estimated_deadline_at` は、course rule によって推定した期限として扱う。

例:

- 「次回講義まで」
- 「次の講義前日 23:59 まで」
- 「授業日の週末まで」
- 「毎週同じ提出ルール」

v0.3 では、確定期限と推定期限を UI で分ける。推定期限は便利なリマインドとして表示するが、確定期限と同じ強さで扱わない。

推奨表示:

- 確定期限: `締切: 2026-06-10 23:59`
- 推定期限: `推定締切: 2026-06-10 23:59`
- evidence 不足: `期限未確認`

## 3. deadline_rule の種類

course rule は、科目ごとに deadline を生成するための rule を持つ。

想定する `deadline_rule`:

- `explicit_only`
  - HTML / Slides 等に明示された期限だけを採用する。
- `next_lecture_start`
  - 次回講義開始まで。
- `previous_day_of_next_lecture`
  - 次回講義の前日まで。
- `previous_day_of_next_lecture_2359`
  - 次回講義の前日 23:59 まで。
- `same_day_2359`
  - 講義当日 23:59 まで。
- `weekend_2359`
  - 講義週の週末 23:59 まで。
- `fixed_weekday_time`
  - 毎週特定曜日・時刻。
- `manual_review_required`
  - ルールだけでは期限を推定しない。候補として表示し、ユーザー確認を必要にする。

v0.3 では rule 名と意味だけを設計し、DB schema はまだ追加しない。

## 4. submission_channel の種類

課題の提出先や確認先は task evidence と同じくらい重要になる。

想定する `submission_channel`:

- `moocs_quiz`
  - MOOCs 上の小テスト・回答フォーム。
- `moocs_report`
  - MOOCs 上のレポート提出。
- `moocs_page_action`
  - MOOCs ページ上のボタンやフォーム。
- `google_form`
  - Google Forms。
- `google_slides_instruction`
  - Slides に提出方法が書かれている。
- `teams`
  - Microsoft Teams 等。
- `email`
  - メール提出。
- `classroom`
  - 授業中提出・口頭確認。
- `external_url`
  - 外部システム。
- `unknown`
  - 推定課題はあるが提出先未確認。

v0.3 では、submission channel は task metadata として保持する想定に留める。

## 5. 科目別想定

### COT101

想定:

- ページ数が多く、演習・レビュー・小テスト・資料ページが混在する。
- MOOCs page_url と MOOCs-Collect pages.key は対応付けできる。
- Slides evidence から演習説明や提出語が取れる可能性が高い。
- HTML evidence だけで全課題を確定するのは難しい。

course rule 案:

- ページ種別が `assignment`, `exercise`, `practice`, `quiz`, `review` に近いものを task candidate にする。
- 明示期限が取れない場合、講義スケジュールから `estimated_deadline_at` を生成する。
- deadline_rule は初期値として `manual_review_required` または `previous_day_of_next_lecture_2359` を検討する。

### SEM101

想定:

- 科目運用ルールから、毎回または特定回に提出物がある可能性がある。
- HTML / Slides に毎回十分な構造化情報が出ない場合がある。
- ユーザーの見落とし防止として推定課題が有効。

course rule 案:

- 講義回ごとに既定 task を生成する。
- 明示 evidence がない場合も `estimated_deadline_at` 付きの推定課題として表示する。
- submission_channel は初期状態では `unknown` または `classroom` / `external_url` の候補扱いにする。
- ユーザー確認が入るまで確定課題には昇格しない。

### COT105

想定:

- AIO page_url と MOOCs-Collect pages.key の join は成功している。
- Google Slides route から SVG aria-label evidence を取得できる可能性がある。
- quiz / report / assignment 系の英語キーワードも混在する。

course rule 案:

- `q1`, `q2`, `report`, `exercise` 等の page slug を task candidate hint として使う。
- Slides evidence の keyword snippet を強めの evidence として扱う。
- 明示期限が取れない場合は course rule による推定期限を別表示する。

## 6. Evidence 統合方針

AIO は task の根拠を複数系統で扱う。

### HTML evidence

MOOCs page HTML から取得する情報:

- page title
- button / form
- deadline-like text
- keyword context
- sign-in redirect status

強み:

- MOOCs ページに直接出ている提出UIを確認できる。

弱み:

- Slides 内の説明を見落とす。
- 期限が本文にない場合がある。

### Slides evidence

Google Slides embed / SVG aria-label から取得する情報:

- 課題・提出・締切関連語の snippet
- deadline candidate
- slide URL / page_key

強み:

- 授業資料に書かれた説明を拾える。
- MOOCs HTML だけでは見えない提出条件を補える。

弱み:

- Google 認証が必要な場合がある。
- aria-label の文字化けや抽出品質に注意が必要。

### Course rule evidence

科目ごとの既定ルールから生成する情報:

- 推定 task title
- estimated_deadline_at
- submission_channel の候補
- confidence
- rule id / rule version

強み:

- HTML / Slides が不完全でも、見落とし防止の候補を作れる。
- 科目運用に合ったリマインドができる。

弱み:

- 誤推定があり得る。
- 確定課題として扱うにはユーザー確認または強い evidence が必要。

### 統合優先度

基本方針:

1. 明示的な HTML deadline があれば `deadline_at`。
2. 明示的な Slides deadline があり、抽出品質が十分なら `deadline_at` 候補。
3. course rule 由来は `estimated_deadline_at`。
4. HTML / Slides / rule が同じ task を指す場合は evidence を統合する。
5. 矛盾がある場合は確定せず、UI で確認が必要な状態にする。

## 7. ユーザー完了チェックとの関係

推定課題は、ユーザーの完了チェックを壊してはいけない。

方針:

- ユーザーが完了にした task は、再importやrule再生成で未完了に戻さない。
- 同じ source key / rule key から生成される task は idempotent に扱う。
- 推定課題が後から確定 evidence を得た場合も、ユーザーの status は保持する。
- 誤推定だった task は、ユーザーが非表示・除外できる必要がある。

将来的には、task に以下のような由来を持たせる。

- `source = html`
- `source = slides`
- `source = course_rule`
- `source = merged`

ただし v0.3 のこのphaseでは DB 実装は行わない。

## 8. UI 方針

v0.3 では確定期限と推定期限を明確に分ける。

UI 表示案:

- 確定課題
  - 通常の task として表示。
  - `deadline_at` を強調。
- 推定課題
  - `推定` ラベルを付ける。
  - `estimated_deadline_at` を表示。
  - evidence snippet または rule 名を確認できるようにする。
- 要確認
  - HTML / Slides / rule が矛盾した場合。
  - 提出先が `unknown` の場合。

重要:

- 推定期限を確定期限のように扱わない。
- 期限未確認のものを勝手に強い警告にしない。
- ユーザーが「これは課題ではない」と判断できる操作を将来用意する。

## 9. 将来の data model 案

まだ実装しないが、将来的には以下のような概念が必要になる。

```text
course_rules
- id
- course_code
- version
- enabled
- deadline_rule
- submission_channel
- task_template
- confidence

task_evidence
- task_id
- evidence_type
- source_key
- snippet
- confidence
- captured_at

tasks
- deadline_at
- estimated_deadline_at
- deadline_confidence
- source
- rule_id
```

このphaseでは schema を追加しない。
