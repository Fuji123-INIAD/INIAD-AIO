# INIAD-AIO v0.3 MOOCs同期 移植前棚卸し

調査日: 2026-06-24  
対象: v0.2のMOOCs取得・PostgreSQL import・Meilisearch登録処理、およびv0.3 SQLiteスキーマ

## 結論

v0.2の処理は、次の3段に分かれている。

1. `backend/moocs_probe.py` がPlaywrightでMOOCsを巡回し、JSONファイルを作る
2. `backend/main.py` がJSONを整形し、PostgreSQLへ保存する
3. `backend/main.py` がPostgreSQLから検索文書を作り、Meilisearchへ全件再登録する

v0.3では、MOOCs巡回処理は概ね流用できる。一方、JSON整形、ID生成、SQLite upsert、同期履歴はDB非依存の正規化層とSQLite永続化層に分離する必要がある。PostgreSQL SQL、FastAPI endpoint、Meilisearch再登録をimporterへ持ち込まない。

Phase 3-1の最小単位は、既存の `moocs_course_details.json` を入力し、`courses / lectures / pages / materials / tasks` を1トランザクションでv0.3 SQLiteへ冪等にupsertする「オフライン importer」とする。Playwright実行、同期API、Meilisearch連携は後続へ分ける。

## 主要エンドポイントと実行入口

### MOOCs取得

MOOCsの科目一覧・詳細を取得するFastAPI endpointはない。取得入口は `backend/moocs_probe.py` のCLIである。

- 通常実行: `probe_courses()` を呼び、`data/probe/moocs_courses.json` を生成
- `--details`: `probe_course_details()` を呼び、`data/probe/moocs_course_details.json` を生成
- `--check-url`: ログイン済みアクセスを確認
- `--save-storage-state`: 永続profileからstorage stateを保存
- `--links-debug` / `--lesson-debug`: DOM調査用

`backend/refresh_cot101.py` は `probe_course_details()` を直接呼び、その後 `POST /api/import-moocs-details` を呼ぶ補助CLIである。

### PostgreSQL import

`backend/main.py` に以下がある。

| endpoint | 関数 | 処理 |
|---|---|---|
| `GET /api/import-courses` | `import_courses()` | coursesをupsert |
| `GET /api/import-lectures` | `import_lectures()` | lecturesを追加 |
| `POST /api/import-pages` | `import_pages()` | ページ本文を追加取得し、pagesをinsert/update |
| `POST /api/import-materials` | `import_materials()` | materialsを追加 |
| `GET, POST /api/import-tasks` | `import_tasks()` | 推定したtasksを追加 |
| `POST /api/import-moocs-details` | `import_moocs_details()` | 複数importと検索再索引を順次実行 |

注意: `import_moocs_details()` の手順は `courses -> lectures -> materials -> tasks -> reindex` で、`import_pages()` を呼んでいない。materialsは既存pagesを要求するため、空DBに対する完全な一括同期にはなっていない。v0.3でこの欠落を踏襲しない。

### Meilisearch

- `POST /api/reindex-search` -> `reindex_search_documents()`
- `import_moocs_details()` の末尾でも `reindex_search_documents()` を実行
- 検索入口は `GET /api/search`

## 主要関数

### `backend/moocs_probe.py`: 取得・JSON生成

- `probe_courses()`: `/courses` を開き、科目一覧を取得してJSON保存
- `extract_with_course_cards()`: `.well` の科目カードから科目名・URLを抽出
- `probe_course_details()`: 科目 -> lesson group -> lesson pageを巡回し、詳細JSONを保存
- `extract_child_links()`: 親URL直下の同一MOOCsドメインリンクを深さで抽出・重複排除
- `extract_content_page_title()`: ページ見出し、document title、URLの順でページ名を決定
- `extract_google_slides_materials()`: Google Slides iframeを資料として抽出
- `course_detail_to_dict()` 以下の変換関数: dataclassをJSON形へ変換
- `load_course_records()` / `course_code_from_url()` / `filter_courses_by_code()`: 一覧JSONの読込と対象科目絞り込み

### `backend/main.py`: 正規化・保存

- `extract_course_code()` / `extract_course_title()`: course JSONの基本情報を正規化
- `extract_lecture_items()`: `lessons` を講義行へ展開。配列順を `lecture_number` とする
- `extract_page_items()`: lesson配下のpagesをページ行へ展開。配列順を `page_number` とする
- `extract_material_items()`: page配下のmaterialsを資料行へ展開
- `extract_task_items()`: ページ・資料のタイトル、URL、種別、本文、期限キーから課題候補を推定
- `normalize_due_date()`: ISO形式の期限だけを `datetime` 化
- `MoocsHtmlTextExtractor` / `page_raw_json_with_extracted_text()`: HTTP、失敗時Playwrightでページ本文を取得し、`extracted_text` を付加
- `import_*()`: PostgreSQL参照・insert/update
- `fetch_search_documents()`: PostgreSQLの5テーブルをMeilisearch文書へ変換
- `reindex_search_documents()`: index設定、全削除、全件追加

## courses / lectures / pages / tasks / materials の取得・整形位置

| 種別 | MOOCsからの取得 | JSON上の形 | v0.2での整形 |
|---|---|---|---|
| courses | `probe_courses()` + `extract_with_course_cards()` | `course_title`, `course_url`, `retrieval_method`, `fetched_at` | `extract_course_code()`, `extract_course_title()` |
| lectures | `probe_course_details()` が科目直下のリンクを `extract_child_links(..., child_depth=1)` で取得 | `lessons[]`: `lesson_title`, `lesson_url`, `pages` | `extract_lecture_items()`。lesson配列順を番号にする |
| pages | 各lesson直下のリンクを同様に取得し、実ページからタイトルを取得 | `pages[]`: `page_title`, `page_url`, `materials` | `extract_page_items()`。page配列順を番号にする。`import_pages()` 時だけ本文を追加取得 |
| materials | 各pageのGoogle Slides iframeを `extract_google_slides_materials()` で取得 | `material_type`, `material_url`, `retrieval_method` | `extract_material_items()` |
| tasks | 専用のMOOCs取得処理はない | 独立したtasks配列もない | `extract_task_items()` がpage/materialをキーワードまたは期限キーで課題と推定 |

### 課題抽出の制約

現行probeが詳細JSONへ保存するpage情報は、基本的にタイトル、URL、Google Slides資料だけである。そのため、課題判定は多くの場合タイトル・URL中の「課題」「提出」「assignment」等に依存し、期限は元JSONに期限キーが存在するときだけ取得できる。

また、`import_pages()` がPostgreSQLの `pages.raw_json` に追加した `extracted_text` は、JSONファイルを読み直す `import_tasks()` の入力には戻らない。したがって、ページ本文の追加取得と課題推定は現状つながっていない。Phase 3-1では既存互換の推定に留め、本文からの高精度な課題・期限抽出は別タスクにするのが安全である。

## データの流れ

```text
MOOCs /courses
  -> moocs_probe.probe_courses
  -> data/probe/moocs_courses.json
  -> moocs_probe.probe_course_details
       course -> lesson links -> page links -> Google Slides iframe
  -> data/probe/moocs_course_details.json
  -> main.py extract_* functions
  -> main.py import_* functions
  -> PostgreSQL courses / lectures / pages / materials / tasks
  -> fetch_search_documents
  -> Meilisearch search_documents
```

ページ本文だけは `import_pages()` の途中で `requests`、失敗時にPlaywrightを使って別途取得され、PostgreSQLの `pages.raw_json.extracted_text` にのみ保存される。

## PostgreSQLに保存している箇所

接続はすべて `backend/main.py` の `get_database_url()` と `psycopg.connect()` を使用する。DDLは `backend/schema.sql`、適用入口は `GET /api/init-db` である。

- `import_courses()`: `ON CONFLICT (course_code) DO UPDATE`
- `import_lectures()`: courseと番号またはtitleで既存確認後にinsert
- `import_pages()`: lectureと番号、title、URLで既存確認しinsert/update
- `import_materials()`: pageと番号またはURLで既存確認後にinsert
- `import_tasks()`: course、title、source URLで既存確認後にinsert

v0.2のIDはPostgreSQL `SERIAL` であり、同期元の安定IDではない。v0.3はTEXT主キーなので、URL由来の `source_key` と決定的ID生成規則が必要になる。

## Meilisearchに登録している箇所

`backend/main.py` の以下に集中している。

- `get_meili_client()` / `get_meili_index()`: 接続とindex取得
- `configure_meili_index()`: searchable/filterable/sortable属性を設定
- `make_search_document()`: 共通検索文書を生成
- `fetch_search_documents()`: PostgreSQLからcourse、lecture、page、task、materialを全件取得
- `reindex_search_documents()`: `delete_all_documents()` 後、`add_documents(..., primary_key="id")`

Phase 3はローカルSQLite同期までを扱い、Meilisearch再登録は実装計画上の後続Phaseへ残す。import成功と検索index成功を同じ成否にしない。

## v0.3で流用するもの

- `moocs_probe.py` のPlaywright context、ログイン確認、科目一覧・詳細巡回
- `Course*ProbeRecord` dataclass群
- `extract_with_course_cards()`
- `extract_child_links()`
- `extract_content_page_title()`
- `extract_google_slides_materials()`
- JSON直列化関数群
- 科目コードのURL抽出と対象科目filter

Phase 3-1ではprobeを改変せず、既存詳細JSONを入力fixtureとして扱う。

### ロジックを抽出して利用可能

- `extract_course_code()` / `extract_course_title()`
- `extract_lecture_items()` / `extract_page_items()` / `extract_material_items()`
- `extract_task_items()` と課題キーワード・期限キー
- `normalize_due_date()`
- 本文取得が必要になった段階で `MoocsHtmlTextExtractor` とHTML整形関数

これらは `main.py` をimportして使わない。`main.py` のimport時にはFastAPI構築、旧SQLite `init_db()`、外部依存の読込が発生するため、純粋関数として `moocs_sync` 配下へ移植する。

## v0.3で切り離す・修正するもの

- PostgreSQL接続、`%s` placeholder、`JSONB` cast、`SERIAL` ID、PostgreSQL JSON演算子
- FastAPI endpointとimport本体の密結合
- Meilisearch再索引の自動実行
- `COURSE_DETAILS_PATH` 固定。importerは入力pathまたはdict/listを受け取れるようにする
- 配列順だけを同一性に使う処理。URL pathを `source_key` にし、並び順は表示順として保存する
- lecture/page/material/taskの「SELECTしてからINSERT」。SQLite `ON CONFLICT` を使える一意性設計または決定的IDにする
- taskのv0.2 `status`。v0.3では同期データと `user_task_status` を分離し、同期時にユーザー状態を削除・上書きしない
- v0.2 taskにない `page_id`, `description`, `first_seen_at`, `last_seen_at` の設定
- v0.2 materialにない `course_id`, `lecture_id`, `title` の設定
- `import_moocs_details()` のpages欠落と、途中失敗時に部分状態が残る手順
- 0件取得時の扱い。認証切れ・DOM変更で既存データを全削除しない
- HTTP/Playwright本文取得をDBトランザクション中に行う構造。取得と保存を分離する

`backend/database.py` と `backend/search_backend.py` はv0.3スキーマではなく旧 `aio.db` 用であり、SQLiteだからという理由で流用しない。`backend/ai_module.py` も同期処理から独立させる。

## Phase 3の分割案

### Phase 3-1: オフラインJSON importer

既存詳細JSONをv0.3 SQLiteへ冪等に反映する。ネットワーク、ブラウザ、FastAPI、Meilisearchを要求しない。

推奨ファイル:

```text
backend/app/core/moocs_sync/
  __init__.py
  importer.py          # JSON検証・正規化・決定的ID・SQLite upsert
  sync_service.py      # transaction、sync_runs、集計結果
tests/
  test_moocs_importer.py
  fixtures/moocs_course_details_minimal.json
```

責務をさらに分ける必要が生じた場合だけ `normalizer.py` を追加する。最初から細分化しすぎない。

決定的ID/source keyの候補:

- course: 正規化した `course_url`（年度を含む）
- lecture: `lesson_url`
- page: `page_url`
- material: `material_url`。同一URL重複時はpage keyと出現位置を併用
- task: `course/page/material` のsource keyと正規化titleの組み合わせ

IDの具体的な文字列表現はPhase 3-1実装時に1つへ固定し、テストで不変性を保証する。

### Phase 3-2: 同期API

- `backend/app/api/sync.py`
- オフラインimporterを呼ぶ薄いendpoint
- 同期中・成功・失敗と件数を返す

### Phase 3-3: MOOCs取得との接続

- 既存 `moocs_probe.py` を取得providerとして呼ぶ
- 取得結果をファイル経由または正規化データとしてsync serviceへ渡す
- 認証切れ、0件、部分取得を失敗として扱い、既存SQLiteデータを保持する

本文取得と課題抽出精度向上、Meilisearch再索引はそれぞれ別Phaseに残す。

## Phase 3-1の完了条件案

- 最小fixtureからcourses、lectures、pages、materials、tasksをv0.3 SQLiteへ登録できる
- 同じ入力を2回importしても行数が増えず、内容が更新される
- course/lecture/page/material/taskのIDが再import後も変わらない
- `raw_json` に元レコードを保持する
- `created_at` / `first_seen_at` は更新時も保持し、`updated_at` / `last_seen_at` は更新する
- task同期後も既存 `user_task_status` が保持される
- 1回のimportをトランザクション化し、途中エラー時に部分反映されない
- `sync_runs` に `running -> ok/error` と件数・エラー概要を記録する
- 無効JSON、必須URL/タイトル欠落、0件入力の扱いがテストされる
- `task_service.list_active_tasks()` が同期済み課題を返す受け入れテストが通る
- `backend/main.py`、v0.2 endpoint、PostgreSQL、Meilisearchの挙動を変更しない

## 実装前に確定すべき小さな設計判断

1. URL由来の決定的ID形式（例: prefix付きhash）
2. 年度の抽出規則（`/courses/{year}/{code}` を基本とするか）
3. 課題推定でpage由来taskへ `page_id` を必ず設定する規則
4. 既存同期に現れなかった行を削除するか。Phase 3-1では削除せずupsertのみを推奨
5. `sync_runs.detail_json` の件数形式

これら以外は、既存JSON fixtureを使うことでネットワークや認証に依存せず実装・検証できる。
