# INIAD-AIO v0.3 Task / Action Item Policy

作成日: 2026-06-24  
対象: INIAD-AIO v0.3 の `tasks` と課題一覧

## 1. 背景

INIADの課題情報は、MOOCs上の提出課題だけでは完結しない。科目や授業回によって、課題の告知場所、提出経路、期限の示され方が異なる。

提出場所として、少なくとも次の形が考えられる。

- MOOCs上で提出する
- メールで提出する
- スライドに提出方法だけが記載される
- 授業中に口頭で説明される
- 別の教材や連絡手段を参照する

期限についても、MOOCs上に明示される場合だけでなく、スライドに記載される場合や、「通常は次回講義の前日まで」のような授業規則から判断する場合がある。

科目ごとの例:

- CS概論Ⅰは週2回講義で、比較的規則的に課題が出る。通常課題に加えて、前回課題の解説動画視聴や自己採点結果の提出など、提出後の関連作業も発生する。ただし、講義曜日は履修者によって異なり、例外回や課題なしの週もある。
- 情報連携学概論ⅠはMOOCs上での提出が中心で、期限もMOOCs上に書かれることが多い。一方、課題内容や期限がスライドにだけ記載される場合もある。
- 情報連携基礎実習Ⅰでは、メール提出が指定される場合がある。

この違いにより、「MOOCs上に提出ボタンがあるもの」だけをtaskとすると、利用者が実際に行う必要のある作業を取りこぼす。

## 2. v0.3での方針

v0.3の `tasks` は、狭い意味の提出課題ではなく、利用者による行動が必要な可能性のある **action item候補** として扱う。

ただし、v0.3では情報源や推定精度がまだ安定していないため、DBスキーマを直ちに拡張しない。推定情報は、まず `tasks.raw_json._aio_task_meta` に保存する。

基本方針は次のとおり。

- `tasks` には提出課題だけでなく、課題に関連する確認・自己採点・振り返り等も保持できる
- 推定した種類と確度は `_aio_task_meta` に保存する
- `deadline_at` には、MOOCsや取得済みデータから明示的に確認できた期限だけを入れる
- 授業規則や講義曜日から推定した期限は、確定期限として `deadline_at` に入れない
- 元データを `raw_json` に残し、後から分類規則を検証・更新できるようにする

## 3. 現在の分類

### `_aio_task_meta.kind`

#### `submission`

明確な提出・回答行動が必要と考えられる候補。

例:

- 課題
- 提出
- レポート
- 小テスト
- Quiz
- Report
- Assignment
- Homework

#### `review_or_feedback`

課題提出後の確認、理解、自己評価、フィードバックに関係する候補。提出物そのものと同じ優先度で扱うとは限らないが、学習フロー上のaction itemになり得るため除外しない。

例:

- 課題解説
- 解説動画
- 自己採点
- 振り返り
- フィードバック確認

#### `weak_candidate`

課題である可能性はあるものの、授業名や一般的なコンテンツ名にも現れやすく、誤検出の多い候補。

例:

- 演習
- exercise
- task
- 一般的な「テスト」表記

### `_aio_task_meta.confidence`

- `high`: 明確な提出語に一致した候補
- `medium`: 関連作業・フィードバックを示す語に一致した候補
- `low`: 弱い語だけに一致した候補

confidenceは提出の重要度や期限の確実性を直接表すものではなく、現在の分類規則による判定確度を表す。

### `_aio_task_meta.reason`

分類に使用したキーワードや規則を、人間が追跡できる文字列として保存する。

例:

```json
{
  "_aio_task_meta": {
    "kind": "review_or_feedback",
    "confidence": "medium",
    "reason": "matched review/feedback keyword: 課題解説"
  }
}
```

## 4. 将来追加したいメタ情報

次の情報は必要になる可能性が高いが、v0.3ではまだDBカラム化しない。情報源と運用が固まるまでは、必要に応じて `_aio_task_meta` 内で試行する。

### `submit_channel`

提出・実施場所。

- `moocs`: MOOCs上で提出・回答する
- `email`: メールで提出する
- `slide_only`: スライドにだけ方法が記載されている
- `unknown`: 提出経路を特定できない

### `deadline_source`

期限情報の根拠。

- `moocs`: MOOCs上の明示情報
- `slide`: スライド上の明示情報
- `rule_estimated`: 授業規則等からの推定
- `unknown`: 根拠を特定できない

### `estimated_deadline_at`

授業規則、講義日程、過去の傾向などから推定した期限。確定期限である `deadline_at` とは分離する。

### `deadline_note`

推定の前提や利用者向けの注意書き。

例:

- 「通常は次回講義前日まで」
- 「スライド記載。MOOCs上では未確認」
- 「履修クラスの曜日により異なる可能性あり」

## 5. 推定期限の扱い

課題の出題と締切に規則性が見られても、推定期限を `deadline_at` に確定値として保存しない。

理由:

- 履修者やクラスによって講義曜日が異なる可能性がある
- 祝日、補講、休講等で通常日程からずれる可能性がある
- 例外的な期限が設定される回がある
- 課題が出ない回や、複数回をまたぐ課題がある
- 推定値を確定値として表示すると、利用者の提出判断を誤らせる可能性がある

将来、推定期限を扱う場合は `estimated_deadline_at` と `deadline_note` を使用し、明示期限とUI上でも区別する。推定の根拠は `deadline_source = rule_estimated` 等で追跡可能にする。

## 6. UI/APIへの示唆

最初の課題一覧では、分類を次のように扱う。

- `submission` を主表示する
- `review_or_feedback` は「関連作業」「提出後の確認」「要確認」等の別枠で表示する
- `weak_candidate` はデフォルトでは隠すか、開発者・利用者向けの確認枠に表示する
- 期限不明の `submission` は「期限不明の提出課題」として表示する
- 期限不明の `review_or_feedback` は、期限不明の提出課題と同列に並べない
- confidenceだけでaction itemを自動削除しない
- 明示期限と推定期限を同じ見た目で表示しない

現在の `tasks` には複数kindが同居するため、件数表示や「未完了課題」という名称も、submissionだけの件数なのか関連作業を含む件数なのかを明示する必要がある。

## 7. 今後の実装候補

- `list_active_tasks()` で `_aio_task_meta.kind` による絞り込みを可能にする
- APIに `include_review=true` のようなオプションを追加する
- `tasks.raw_json._aio_task_meta.kind` を読み取り、submission / review / weakを分けたレスポンスを返す
- `submission` をデフォルト、`review_or_feedback` を任意表示、`weak_candidate` を非表示とする既定動作を検討する
- MOOCs、スライド、メール等から `submit_channel` と `deadline_source` を補完する
- 推定期限を実装する場合、履修者ごとの講義曜日設定と例外処理を先に設計する
- 運用実績とクエリ要件が固まった段階で、頻繁に検索・絞り込みするメタ情報をDBカラムへ昇格するか検討する

DBカラムへの昇格は、分類値が安定し、SQLiteのJSON参照だけでは検索・更新要件を満たせないと確認してから行う。
