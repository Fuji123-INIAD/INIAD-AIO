# INIAD-AIO v0.3 Deadline Normalization Policy

作成日: 2026-06-26  
対象: MOOCs HTML から取得した `deadline_text_candidates` の分類・正規化方針

## 目的

Phase 3-6 / 3-7 で、MOOCs page HTML 由来の期限候補を `deadline_text_candidates` として probe JSON および `tasks.raw_json._aio_task_meta` に保持できるようになった。

Phase 3-9 では、これらの期限原文を将来どのフィールドへ分けるかを設計する。今回はコード変更、DBスキーマ変更、`deadline_at` 正規化実装は行わない。

## 基本方針

`deadline_at` は、明示期限を安全に正規化できた場合だけ使う。

例:

- `4月21日火曜日23時59分`
- `2026年4月21日 23:59`
- `2026-04-21 23:59`

ただし、年・タイムゾーン・日付表現・曜日の整合性を確認できない場合は、無理に `deadline_at` へ入れない。ローカルアプリであっても、安全寄りに扱い、誤った確定期限を表示しないことを優先する。

相対期限や授業規則由来の期限は、`deadline_at` に入れない。

例:

- `次の講義前日まで`
- `次回授業まで`
- `通常は次の講義の前日まで`
- `授業中に指示された期限`

これらは原文証拠として保持し、将来 `estimated_deadline_at` と `deadline_note` の候補にする。

## フィールドの分担案

### `deadline_at`

確定期限。ユーザーに「この日時が期限」と表示できる場合だけ設定する。

設定条件:

- 原文に具体的な日付または日時がある
- 年度または年を安全に補える
- タイムゾーンを `Asia/Tokyo` として扱ってよい根拠がある
- 曜日が書かれている場合、日付と矛盾しない
- 複数候補がある場合、どれが提出期限か判断できる

不明点が残る場合は `deadline_at` を `NULL` のままにする。

### `estimated_deadline_at`

推定期限。相対期限や授業規則から計算した候補を入れる。

例:

- `次の講義前日まで`
- 講義日インスタンスから「次回講義の前日 23:59」を推定

推定には次の根拠が必要になる。

- 時間割テンプレート
- 学年暦
- ユーザーの履修クラス設定
- 講義回と実施日の対応
- 休講・補講・曜日振替などの例外

`estimated_deadline_at` は `deadline_at` と同じ見た目で扱わない。UI上も「推定」と明示する。

### `deadline_note`

期限原文や推定上の注意をユーザーに伝えるための補足。

例:

- `MOOCs原文: 次の講義前日まで`
- `授業日程から推定。休講・補講・曜日振替で変わる可能性があります。`
- `クラス設定が未確定のため推定できません。`

### `deadline_text_candidates`

MOOCs HTML から取れた原文証拠として保持する。正規化に失敗しても捨てない。

用途:

- 後続の deadline parser 改善
- UIでの根拠表示
- 誤分類調査
- 手動確認

`deadline_text_candidates` は「候補」であり、確定期限ではない。

## 明示期限と相対期限の分類

### 明示期限

日付や時刻が直接書かれているもの。

例:

- `4月21日火曜日23時59分`
- `6/10 23:59`
- `2026-06-10 23:59`

処理方針:

1. 原文を `deadline_text_candidates` に保持する
2. course 年度や取得元情報から年を補えるか検証する
3. `Asia/Tokyo` として解釈できるか検証する
4. 曜日があれば整合性を確認する
5. 安全に正規化できた場合だけ `deadline_at` を設定する

### 相対期限

授業日や講義回に依存するもの。

例:

- `次の講義前日まで`
- `次回講義まで`
- `次回授業の前日`

処理方針:

1. 原文を `deadline_text_candidates` に保持する
2. `deadline_at` には入れない
3. 将来、講義日インスタンスが生成できる場合のみ `estimated_deadline_at` 候補にする
4. UIでは推定であることと根拠を表示する

## accepting status との分離

`accepting_status_text` と deadline は別概念として扱う。

例:

- `現在回答を受け付けていません`
- `提出を受け付けています`
- `提出済み`

これらは受付状態の証拠であり、期限そのものではない。`accepting_status_text` が `closed` 相当でも、`deadline_at` を推定してはいけない。

逆に、`deadline_at` が未来でも、MOOCs 側の受付状態が閉じている可能性はある。UIでは期限と受付状態を別々に表示・判断する。

## UI表示方針

UIでは確定期限と推定期限を明確に分ける。

表示案:

- 確定期限: `期限: 2026-04-21 23:59`
- 推定期限: `推定期限: 2026-04-20 23:59`
- 期限原文のみ: `期限候補: 次の講義前日まで`
- 不明: `期限未確認`

推定期限には、必ず注意書きを付ける。

例:

```text
授業日程からの推定です。休講・補講・曜日振替・クラス差分により変わる可能性があります。
```

ローカルアプリであっても、ユーザーが提出判断を誤らないよう、安全寄りに扱う。

## 将来の lecture_date_instances 生成案

将来、相対期限を `estimated_deadline_at` に変換するには、講義日インスタンスが必要になる。

根拠候補:

- 2026春学期の東洋大学学年暦PDF
- 1年必修時間割
- ユーザーの履修クラス設定
- MOOCs の course / lesson / page 構造

生成イメージ:

1. 学年暦PDFから授業実施期間、祝日、補講日、休講期間を取り込む
2. 1年必修時間割から科目・クラス・曜日時限を取り込む
3. ユーザーの履修クラス設定で該当曜日時限を選ぶ
4. course / lesson の順序と講義日を対応付ける
5. `次の講義前日まで` を次回講義日の前日として推定する

注意点:

- 曜日振替がある
- 休講がある
- 補講がある
- クラス差分がある
- MOOCs の lesson 番号と実際の講義日が常に一致するとは限らない
- 例外的に個別課題だけ異なる期限が設定される可能性がある

そのため、生成した値はまず `estimated_deadline_at` として扱い、`deadline_at` には昇格しない。

## 段階的な実装案

### Phase A: 原文保持

現状の方針。

- `deadline_text_candidates` を `_aio_task_meta` に保持
- `deadline_source_candidate = "moocs_html"` を保持
- `deadline_at` は変更しない

### Phase B: 明示期限 parser

明示期限だけを対象にする。

- 年月日・時刻表現を parse
- course 年度から年を補完
- 曜日整合性を確認
- 安全に正規化できる場合のみ `deadline_at` を設定
- 失敗時は `deadline_text_candidates` と `deadline_note` に留める

### Phase C: 推定期限

相対期限を扱う。

- 学年暦・時間割・履修クラス設定から `lecture_date_instances` を生成
- `次の講義前日まで` を `estimated_deadline_at` 候補に変換
- UIでは推定として表示

### Phase D: 運用評価

実データで誤分類や過剰推定を確認する。

- `deadline_at` と `estimated_deadline_at` の混同がないか
- 受付状態と期限表示が矛盾して見えないか
- ユーザーが提出判断に使える表示になっているか

- `deadline_note` 実装
